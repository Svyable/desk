# The Backup That Wasn't

A backup is one of the most comforting nouns in technology.

It sounds like a thing.

A copy.

A second chance.

A small insurance policy sitting somewhere quiet while production gets on with life.

Then somebody needs it.

In January 2017, GitLab experienced a major database outage after production data was accidentally removed from the primary database server. The incident became famous partly because GitLab handled it in public, publishing a detailed postmortem and even streaming parts of the recovery.

The most useful part of the story is not the accidental deletion.

Accidental deletion is easy to understand.

The useful part is what happened when the organization reached for recovery.

The normal database backup procedure was not available in the way everyone needed it to be.

GitLab’s postmortem described a `pg_dump` backup process that had been failing because it used PostgreSQL 9.2 tooling against a PostgreSQL 9.6 database. The intended backups were not sitting safely in the expected S3 bucket. Other recovery paths had problems too. Replication was not a disaster-recovery backup. Disk snapshots were not available on the database servers in the required way. The restore eventually depended on data from a staging environment and took many hours.

The company’s own root-cause analysis asked the right question:

Why had the backup procedure not been tested regularly?

The answer was brutally ordinary.

There was no clear ownership.

Nobody was responsible for proving that the comforting noun was a working verb.

## Possession is not recovery

AI systems are accumulating their own versions of imaginary backups.

“We can always switch models.” “We export everything.” “The prompts are in Git.” “We still have the manual process.” “There is a second provider.”

“We log every action.” “The human can take over.” “We can rebuild the index.” “We can recreate the memory.” Maybe.

The existence of an artifact is not evidence of recovery.

A data export may omit relationships that the application reconstructs internally.

A prompt repository may contain text but not the hidden configuration, tool schemas, memory state, permissions, routing rules, and model-specific assumptions that make the workflow behave.

A second provider may support the same nominal API while producing different tool-call patterns or context behavior.

A manual process may technically exist while the team no longer has enough people to operate it at production volume.

Logs may be complete but impossible to replay.

A human override may work for ten cases and collapse under ten thousand.

Recovery is not owning pieces.

Recovery is being able to re-establish an acceptable function from those pieces within the time and quality the business can tolerate.

## The restore is the test

There is an old operations lesson that deserves to become an AI lesson:

Do not test the backup.

Test the restore.

A backup test asks whether the file exists.

A restore test asks whether the system can come back.

That difference is enormous.

Imagine an organization that exports all of its AI memory every night.

Excellent.

Can a new system ingest it?

Does the export contain timestamps, provenance, user permissions, deletion states, and the distinction between durable facts and transient conversation?

Can the organization tell which memory came from the user, which was inferred by a model, and which was generated by an old workflow that no longer exists?

Can another model use the records without inheriting stale assumptions?

If the export is technically complete but practically unintelligible, the backup exists and the recovery does not.

The same test applies to evaluation.

You may have an eval suite.

Can it be run against a replacement model today?

Does it still contain the edge cases that matter?

Are the expected answers current?

Can the team interpret a regression?

Does passing the eval mean the workflow is safe to migrate, or only that the model can answer isolated prompts?

An evaluation harness can be a recovery asset.

Only if it is operational.

## Replication is not a backup

GitLab’s incident also illustrates a distinction that becomes critical in AI architecture.

Replication and backup solve different problems.

A replica protects against one kind of failure.

If the primary machine dies, another copy may take over.

But if the primary system faithfully performs a bad operation and the replica faithfully copies it, replication has preserved the mistake.

The redundancy is real.

The recovery value is not.

AI systems are full of this kind of correlated redundancy.

A company may route one request to two models but provide both models the same poisoned retrieval context.

Two agents may independently review a transaction while reading the same incorrect source record.

Two providers may both rely on the same customer identity service.

A primary workflow and its “backup” may share the same vector database.

A human reviewer may rely on the AI-generated summary instead of the underlying evidence, reproducing the same error through a different interface.

A second agent may critique the first while receiving the same misleading instruction.

The copies differ.

The failure source does not.

When designing recovery, ask what failure you are trying to survive.

Hardware loss? Provider outage? Bad model behavior? Corrupt data? Compromised credentials?

A mistaken policy? A malicious user? An internal operator error? A model migration? A legal requirement to reconstruct a decision?

Different failures require different kinds of independence. There is no universal backup.

## Recovery has a clock

One of the quiet surprises in disaster recovery is that a recovery path can work and still fail the business.

Suppose the data can be restored in four days.

Technically, good news.

If the company can tolerate four hours, the recovery objective was missed.

Suppose the manual workflow can handle twenty customer requests an hour.

Useful.

If normal traffic is twenty thousand, the organization has not preserved service. It has preserved a demonstration.

Suppose a replacement model can be integrated in two weeks.

That may be excellent for a strategic migration.

It may be useless during a provider outage.

So every important fallback needs a clock. How quickly must it start? How long can degraded operation continue? How much backlog can accumulate? What data can be lost?

What quality loss is acceptable? What obligations continue during the disruption?

The infrastructure world has formal vocabulary for this: recovery time objectives, recovery point objectives, service-level objectives.

You do not need the acronyms to use the thinking.

Ask how much time and loss the function can tolerate.

Then design the fallback to that reality.

## The human fallback fantasy

AI teams often treat people as the ultimate backup.

If automation fails, humans will take over.

Humans are wonderfully flexible.

That flexibility creates a dangerous planning assumption.

A manual fallback can fail in at least five ways.

The skill is gone.

The scale is too large.

The information arrives in a machine-oriented form humans cannot use.

The people with authority are not the people with knowledge.

The fallback has not been exercised under current conditions.

Consider a support operation where an agent resolves eighty percent of cases.

Over time the team gets smaller.

The remaining humans focus on unusual escalations.

Then the agent becomes unavailable.

Can the human team absorb the ordinary cases again?

Maybe for an hour.

Maybe not for a week.

Maybe the old user interface has been removed because nobody used it.

Maybe knowledge articles were rewritten for agent retrieval and became unpleasant for humans to navigate.

Maybe staffing assumptions make full manual operation economically impossible.

“The humans will take over” is not a plan until you know what volume they can take, what tools they will use, and which service levels will be abandoned.

Graceful degradation is more realistic.

The system may not return to the old manual world.

It may reduce service. Accept only high-priority cases. Disable complex actions. Move from immediate response to queued response. Offer deterministic answers for known questions.

Stop a feature safely.

Preserve the essential function while admitting that quality has fallen.

That is stronger than pretending the full service survives.

## Ownership is a control

The sentence from GitLab’s postmortem that matters most is not technical.

The backup procedure lacked ownership.

This is common because recovery systems live outside the happy path.

Nobody receives applause because the restore worked during a quarter when nothing failed.

The feature team ships visible improvements. The fallback quietly ages. Credentials expire. Formats change. People leave.

A script keeps running with warnings nobody reads.

A second provider drops support for an old endpoint.

A manual runbook references a screen that disappeared last year.

The organization feels protected because the artifact still exists.

Ownership changes that.

A fallback needs a person or team responsible for its continued truth.

Not necessarily someone who operates it every day.

Someone who can answer: When was this last tested? What changed since then? What does it protect us from? What does it not protect us from?

How long will it work? What would cause us to retire it? That last question is important.

A robust organization does not preserve every backup forever.

Some fallbacks should die.

If the primary system becomes so different that the old fallback no longer serves the business, maintaining it can create false confidence and wasted complexity.

Retire it deliberately.

Replace it with a fallback that matches the current system.

## The restore day

Once or twice a year, pick one critical AI-enabled workflow and pretend the preferred path is gone.

Not in a tabletop conversation only. Actually move. Use the export. Start the second model. Invoke the degraded mode.

Move a small real workload through the fallback if the risk allows.

Measure the time. Watch for undocumented dependencies. Find the password nobody has. Find the schema that changed.

Find the human step that takes six minutes per case.

Find the evaluation that no longer runs.

Find the team that does not know it owns the decision.

Find the customer promise that makes the degraded mode unacceptable.

Those discoveries are not evidence that the resilience program failed.

They are the value of the exercise.

A restore test converts imaginary robustness into observed robustness.

## The comforting noun

Technology is full of nouns that make organizations feel safer than they are.

Backup. Fallback. Redundancy. Override. Export.

Rollback. Replica. Archive. Runbook.

Each noun should be translated into a verb.

Can you restore? Can you fall back? Can you switch? Can you override? Can you import the export?

Can you roll back?

Can the replica survive the failure you care about?

Can you retrieve the archive?

Can a tired operator follow the runbook at three in the morning?

Sturdiness lives in the verbs.

The backup you have not restored is a belief.

Test the belief before you need the fact.
