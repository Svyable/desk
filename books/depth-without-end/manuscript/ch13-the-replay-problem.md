# Chapter 13 — The Replay Problem

Reinforcement learning likes to pretend the past can be replayed.

A policy acts. The trajectory is recorded. Later, the policy is updated and the recorded actions are used to improve it. This is ordinary enough that words such as *rollout*, *replay*, and *batch* can make the process sound like bookkeeping.

For a stateful recurrent model, bookkeeping becomes part of the mathematics.

The problem begins with a deceptively simple fact: the hidden state you had yesterday may not be the hidden state today's model would have had.

Suppose a model reads a prompt and generates an answer under parameter set `θ_old`. During that sequence, each recurrent state is produced by applying the model's transition to the previous state and the current input. The resulting trajectory contains not only visible tokens but parameter-dependent hidden states, decoder key-value caches, and encoder-derived memories.

Then training changes the parameters to `θ_new`.

If we replay the same visible token sequence, the current model may produce a different internal trajectory from the first prompt token onward. By action ten, the difference can be substantial. The old token sequence is still the same. The policy state from which those tokens were chosen is not.

This matters whenever the learning algorithm asks a question about the *current policy*.

What probability does the current policy assign to an action that was sampled earlier?

For a stateless classifier, evaluate the current model on the stored input. For an ordinary autoregressive Transformer, reconstruct the preceding tokens and compute the action probability with current weights. The attention cache can be rebuilt from the visible history.

For RLT, the visible history is necessary but the current recurrent state must also be reconstructed from it under current parameters.

Zhang's report insists on this execution rule. Current-policy replay rebuilds the complete history, including prompt recurrence and decoder sliding-window caches. Actions are evaluated before being consumed, at the state the current policy would occupy after processing the prior history.

This is easy to describe and expensive to respect.

Imagine a rollout containing an 8,000-token prompt and a 2,000-token response. The policy has already paid to generate the response once. After weights change, exact replay cannot simply load the old final hidden state and score the answer. The state is stale. The recurrent decoder must traverse the history again under current weights to reconstruct what the present policy would have believed at each action.

The architecture turns the prompt into part of the policy state transition.

This is philosophically coherent. It is operationally brutal.

Why not store the old hidden state and use it anyway?

You can.

Then you are evaluating a hybrid object: current parameters acting from a state produced by old parameters. That hybrid may be a useful approximation. It is not the exact current policy implied by the recurrent architecture.

This distinction matters because reinforcement learning already lives with approximations. Policy-gradient methods use sampled trajectories. PPO-style objectives clip importance ratios. Off-policy methods reuse data generated by earlier policies. Value estimates are imperfect. Rewards can be noisy. The field is not waiting for mathematical purity before training anything useful.

The question is whether stale recurrent state introduces a bias large enough to matter.

That is an empirical problem.

The answer will depend on how quickly state changes when parameters move, how long trajectories are, which parts of the state carry decision-critical information, and how aggressively training updates the policy between rollout and replay.

A small update might leave trajectories close enough that stale state is harmless.

A large update might change the prompt interpretation, causing every later action probability to be evaluated from the wrong latent premise.

The error can compound because recurrence feeds its own output forward. A slight difference in state at token 100 becomes an input difference at token 101, which creates another difference at 102. Even if the transition is locally stable, thousands of steps can make stale and current trajectories diverge.

This is the same long-path problem seen from the other side.

During training, gradients ask how a later loss depends on earlier state.

During replay, policy evaluation asks which earlier state the current parameters would actually have created.

Both questions force history back into the present.

The decoder key-value cache creates a related issue. In a Transformer, cached keys and values are functions of the parameters used to produce them. If weights change, exact current-policy evaluation should not reuse stale parameter-dependent caches as though they were neutral data. RLT adds recurrent state to the list of things that may need reconstruction.

The causal encoder memory is parameter-dependent too.

The architecture's clean execution semantics therefore create a large recomputation burden after updates.

This burden could become one of the decisive practical differences between recurrent-state models and architectures that keep more state in visible tokens or external artifacts.

A text trajectory is portable across model versions. A hidden trajectory is not.

That sentence has consequences far beyond reinforcement learning.

Suppose an agent runs for six hours, accumulating a rich recurrent state, and the serving system hot-swaps to an improved checkpoint. Can the new model inherit the old state? If the state was produced under different weights, its coordinates may no longer have the same meaning. The system may have to replay the entire visible history, translate state between versions, or reset.

Suppose a model crashes. If only the final recurrent tensor was checkpointed, can another replica resume deterministically? Only if the model version, numerical kernels, cache state, and execution details are compatible enough. A transcript is easier to recover from because it is not already interpreted by one parameterization.

Suppose researchers want to reproduce a harmful output. The prompt and generated tokens may be insufficient to reproduce the hidden trajectory if nondeterministic kernels, sampling details, or model revisions differ.

State makes execution history more consequential.

This is why RLT's insistence on one execution semantics across pretraining, supervised fine-tuning, sampling, and reinforcement-learning replay is more than tidiness. Architectural mismatches between modes can create hidden distribution shifts.

If pretraining updates state on every token but fine-tuning resets at the prompt boundary, the model is trained to use recurrence under one regime and deployed under another.

If rollout generation carries prompt recurrence but replay starts from a cached boundary state, the policy being optimized differs structurally from the policy that acted.

If inference uses a fused kernel whose numerical behavior differs from the training kernel enough to alter long recurrent trajectories, a tiny mismatch can amplify over time.

The report explicitly notes that shared execution semantics do not alone guarantee numerical kernel parity. That caveat is easy to skip and worth dwelling on.

Modern deep-learning systems routinely use different kernels for prefill and decode because their shapes differ. A large prompt can be processed as a matrix; one-token decoding has different memory and arithmetic patterns. Quantization, fused attention, reduced precision, and compiler choices can introduce small numerical differences.

In a feed-forward model, small differences may perturb one forward pass.

In a recurrent model, a perturbation can become tomorrow's input.

Numerical reproducibility therefore becomes a dynamical-systems question. Does the recurrence damp small perturbations or amplify them?

A stable recurrent architecture should not require bitwise-identical kernels to behave coherently. If a one-bit floating-point difference sends the state toward a different answer after a thousand steps, the system is too fragile for ordinary deployment. But the acceptable tolerance has to be measured.

This suggests a benchmark almost nobody puts on a leaderboard: kernel perturbation stability.

Run the same sequence using different mathematically equivalent attention kernels, precisions, or batch layouts. Measure how recurrent states diverge and whether output quality changes. Inject tiny controlled noise into state. Track the Lyapunov-like behavior of the learned dynamics. A model whose useful trajectory is robust should absorb ordinary numerical variation.

The replay problem also touches importance sampling.

In off-policy reinforcement learning, data may have been generated by a behavior policy different from the policy being optimized. Importance ratios correct, under specific assumptions, for that mismatch by comparing action probabilities under target and behavior policies.

For an autoregressive language model, the behavior log-probability of each sampled token should describe the actual distribution from which that token was drawn. Temperature, top-k or top-p truncation, rejection sampling, and other sampling transformations matter. The base model's raw softmax is not necessarily the behavior distribution.

Zhang's report points out another requirement: exact importance sampling needs support coverage. If the behavior policy assigns zero probability to actions the target could take, no finite ratio can correct the missing support.

These are standard RL facts with sharp consequences for increasingly complicated language-model samplers.

A recurrent architecture does not create the support problem. It makes the policy state at which probabilities are evaluated more elaborate.

The full behavior policy is not merely “weights plus temperature.” It includes the recurrent state produced by the behavior trajectory, cache semantics, prompt processing, and sampling transformation.

Once again, the system matters more than the checkpoint.

This is a theme that AI evaluation keeps rediscovering. We want a model to be an object with a name. Reinforcement learning reveals a process: policy, state, sampler, environment, replay, update. Recurrence deepens that process dependence because hidden history is part of the current action distribution.

There are several possible engineering responses.

One is brute-force exact replay. Recompute prompt and response state under current weights. This preserves the clean semantics and pays the cost.

Another is shorter update intervals or smaller parameter changes so stale-state approximations remain close.

Another is to checkpoint intermediate visible histories and replay from selected points, though hidden state at the checkpoint is still parameter-dependent unless recomputed.

Another is to learn a state-translation function between nearby policy versions. That would be elegant and dangerous: now the correctness of RL depends on a second model accurately mapping one hidden geometry into another.

Another is to detach parts of the state and accept biased gradients or approximate policy evaluation, then measure whether the bias affects outcomes.

Another is to design recurrent state with stronger version stability, perhaps by constraining a subset of the state to standardized semantics. This sacrifices some unconstrained representation capacity for portability.

None is obviously best.

The choice will depend on whether recurrent state produces enough capability to justify the operational machinery.

This is an important corrective to architecture discussions that end at benchmark accuracy. A model deployed at scale participates in a lifecycle. It is trained, sampled, updated, evaluated, checkpointed, served, rolled back, quantized, replicated, and sometimes changed while workloads continue. A stateful architecture can make every stage more coupled to the others.

RLT calls this model–RL algorithm co-design.

The phrase is accurate but abstract. The concrete meaning is that the model architecture can determine which RL algorithms remain exact, which caches are reusable, how expensive policy evaluation becomes, and what constitutes the state of the policy.

A clever recurrent transition may therefore lose to a less elegant architecture if the latter is dramatically easier to train with large-scale RL.

The reverse can also happen. An architecture that makes state explicit and consistent may remove subtle mismatches that plague current training systems. Recomputing exact state can be expensive while providing a cleaner objective. If that objective produces more stable learning or better credit assignment, the extra systems work may pay for itself.

We do not yet know.

The important part is that the question can be stated precisely.

Take a recurrent policy trained with current-policy RL. Compare exact reconstruction against stale-state replay under controlled update sizes. Measure objective bias, gradient direction, reward improvement, stability, and cost. Repeat across sequence lengths. Identify when the approximation begins to fail.

Then compare with a non-recurrent baseline spending the same total training compute.

That experiment would tell us whether the replay problem is an implementation nuisance or a fundamental tax on recurrent reasoning.

There is a broader lesson hiding behind it.

State is not free simply because you can store it.

A state has provenance. It was produced by a model version, from a history, under a numerical execution, with particular caches and sampling decisions. Once the state influences future actions, that provenance becomes part of the policy.

The more intelligence we try to place in persistent latent state, the more seriously we have to take the lineage of that state.

Reinforcement learning merely forces the issue first because it keeps asking the present model to account for the actions of its recent past.
