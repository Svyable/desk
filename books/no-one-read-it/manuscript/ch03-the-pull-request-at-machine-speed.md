# The Pull Request at Machine Speed

At 10:01 on the morning of May 26, 2026, a pull request appeared in the public repository for `flake8-bugbear`, a Python linting tool. Its title identified it as one possible solution to an open issue. Its description identified something else: the proposal had been generated by AI and had not yet been reviewed by a human.

Sixteen seconds later, a second solution appeared.

Both came from a research team at JetBrains. They addressed the same request for a new lint rule. The proposed rule concerned a small but real ambiguity in Python code: a programmer could combine several iterables with `zip`, assign one of the resulting values to an underscore, and appear to signal that the value was unused. The issue asked whether the linter should flag that pattern.

The two pull requests offered maintainers a choice. The accompanying note asked them to inspect the alternatives and spend roughly ten minutes reporting which they preferred. The submissions were public, compact, and explicit about their origin. Nothing had been smuggled into the project.

Then review began.

An automated reviewer examined the first proposal and found several concerns. Some were mechanical. The new code had a formatting problem that could make the project fail its own linting rules. Some were structural. The implementation risked treating assignment targets as if they were later uses and mishandling names in different scopes. It reused a diagnostic number that the project had retired. It did not include the test files normally used to evaluate new rules.

The second proposal was shorter. It also arrived without tests. More importantly, the automated review found a question about behavior. An iterable passed to `zip` can determine when the loop ends even if the program ignores every value it contributes. Removing that iterable would not merely tidy the code. It could change how many times the loop ran.

This is the kind of error that a fluent explanation can glide past. A variable named with an underscore looks unused. At the level of the line, the advice to remove it feels clean. At the level of execution, the supposedly unused input may still be doing work.

A maintainer considered the two alternatives. He preferred the second, provided tests were added, and described a workflow in which he used AI review and then performed a sanity check. This was not a human valiantly catching what the machines could not. One machine had generated the patch. Another had surfaced a plausible semantic problem. The human was deciding whether the change fit the project and what evidence would make it acceptable.

The feedback loop stopped there. The researchers clarified that the two pull requests had been submitted for a study. Neither was meant to be merged, and they could not be updated in response to review. The maintainer then explained that the arrangement should have been disclosed more clearly. His limited time had been used to evaluate work that could not become a contribution to the project.

Both pull requests were closed.

The episode is modest by the standards of software failure. No outage followed. No vulnerability was released. The repository's controls worked: the proposals remained proposals. Yet the record captures a production problem with unusual clarity. Two patches could arrive almost simultaneously. Automated review could begin almost immediately and find real issues. The scarce input was the attention needed to choose, test, explain, and revise—and the capacity of an author to remain in the exchange until the work was ready.

A pull request is often described as a package of code awaiting approval. That description leaves out its most useful property. It is a place where a change can answer questions before becoming infrastructure.

Why this approach? What behavior is supposed to change? What else could change with it? Which tests fail before the patch and pass after it? Is there a smaller version? Does the contributor understand the project's conventions? Can the author respond when a reviewer discovers that the proposed fix breaks another case?

The code is only one participant in that conversation.

Modern code review grew around the fact that software production is collaborative memory. A 2018 study by Caitlin Sadowski and colleagues examined the review practices supporting Google's codebase. It drew on interviews, a survey, and roughly nine million reviewed changes made by more than twenty-five thousand authors and reviewers. The typical change was small: the median modified twenty-four lines, and about ninety percent touched fewer than ten files. More than eighty percent completed with at most one round of revision.

Those numbers do not describe every engineering organization, but they show a system shaped to keep changes comprehensible. Smallness matters because a reviewer does not inspect lines independently. The reviewer has to reconstruct intent, follow effects, compare the change with conventions, and decide what future maintainers will be able to understand. Sadowski's respondents valued review not only for finding defects but also for improving understandability and keeping knowledge inside the organization.

Research at Microsoft found a similar range of purposes. Reviewers and authors used the process to understand changes, transfer knowledge, maintain team awareness, and discover alternative solutions. Defect finding mattered, but the practice was not reducible to a bug filter.

This broader purpose explains why a passing test suite does not complete a review. Tests are evidence about selected behavior. They are extraordinarily useful precisely because they are executable and repeatable. But the suite reflects what somebody thought to test. It may not reveal that a new dependency is hard to maintain, that an interface has become confusing, that a shortcut violates a system boundary, or that the change solves the wrong problem elegantly.

Review joins evidence to responsibility. A test can say that an example passed. A type checker can say that certain inconsistencies were absent. A security scanner can match known patterns. A reviewer has to decide what the project is prepared to own.

Generative coding tools alter the cost of arriving at that decision. A developer can request an implementation, ask for tests, produce documentation, and open a pull request without composing each line. An agent can search the repository, edit multiple files, run checks, and respond to failures. The gain can be substantial. It can also appear at the wrong point in the accounting.

The visible output is code. The absorbed output is a maintained change.

Between them sits the review budget.

Consider what happens when a team doubles the number of plausible proposals while holding the number of experienced reviewers constant. The queue grows. Each reviewer can spend less time per proposal, allow waiting time to increase, or reject more work at the boundary. If performance is measured by pull requests opened, the system looks more productive. If it is measured by changes safely understood and maintained, the result is uncertain.

The team may respond by automating review. That is often the right response. Linters catch style and correctness errors. Type systems expose mismatches. Test suites exercise behavior. Coverage tools show which modified lines were reached. Static analysis looks for vulnerable flows. Model-based reviewers can describe suspicious interactions in ordinary language. Each check can remove work from the human queue.

The automated review of the two `flake8-bugbear` proposals demonstrates this positive case. It found issues a maintainer should want to know about. The relevant question is not whether the comment came from a person. It is whether the check supplied independent evidence.

Independence is difficult. A model asked to review code generated by a similar model may share its blind spots. A test generated from the same mistaken interpretation as the implementation may confirm the interpretation perfectly. A summary can repeat the author's stated intent without examining the executed behavior. Several green checks can be several views of the same assumption.

The number of reviewers therefore matters less than the diversity of what they can observe. Compilation observes one thing. A regression test observes another. Production telemetry, adversarial tests, code ownership, and a maintainer's knowledge of prior failures observe others. A useful review stack does not merely multiply verdicts. It creates different opportunities for the proposal to fail.

GitHub's own workflow for coding agents reflects this distinction. Its guidance says that agent-created pull requests should receive the same thorough review as human-authored ones. The agent's own approval does not ordinarily satisfy a requirement for another reviewer, and workflows triggered by its pushes do not automatically run by default without a human decision. These are not proofs that every approved change is safe. They preserve separation between producer, evidence, and authority.

The pressure to erase that separation will be strong because review looks slower than generation. A coding demonstration can create a feature in minutes. A serious review contains pauses, questions, reruns, and sometimes a refusal to merge. If the organization treats delay as waste, the reviewer becomes the obstacle in every productivity story.

Evidence about coding speed makes the temptation worse because the reported effects vary so widely. In a controlled task, researchers found that developers with access to GitHub Copilot completed an HTTP-server exercise much faster than developers without it. The task was fixed, the completion condition observable, and the setting favorable to measuring production time.

In a different study, METR worked with experienced open-source developers performing real tasks in repositories they knew well. In early 2025, the developers expected the allowed AI tools to make them faster and later believed they had done so. The measured result went the other way: they took longer. The researchers discussed several reasons the setting might produce that result, including the maturity of the tools, the complexity of the repositories, and the cost of checking and correcting output.

The result did not settle the question. METR later reported that a follow-up experiment with newer tools could not support a reliable estimate. Developers selected different tasks depending on whether they chose to use AI, some work moved into parallel agents, and time measurement became harder. The group thought newer tools were probably more useful, but declined to turn the data into a clean speed number.

This uncertainty is not an annoyance surrounding the real story. It is the story. “Coding” names several different activities. Producing a familiar function in a controlled exercise is not the same as changing a mature repository under maintenance constraints. A tool can accelerate typing, initial implementation, exploration, documentation, tests, or debugging by different amounts. It can save the author time and cost the reviewer time. It can slow an expert on a particular task while helping a newcomer form a map of the codebase.

There is no honest universal multiplier.

There is, however, a better-shaped unit of work.

Two months before the `flake8-bugbear` experiment, another AI-authored pull request appeared in a neighboring PyCQA project. The project was `isort`, a widely used formatter for Python imports. The proposed fix added one line to the implementation and a regression test. The test captured the behavior at issue. Coverage tooling reported that the modified coverable lines had been exercised. A human maintainer approved the change. It was merged about ten minutes after it opened and later credited in the project's release notes.

The contrast is not that the `isort` agent was good and the `flake8-bugbear` agents were bad. The first change carried a way to prove the narrow claim it made. It was small enough to reconstruct. It fit a live maintenance process. A human with project authority could inspect it, approve it, and allow it to become part of the codebase. If a reviewer had objected, the contribution had an owner and a path toward revision.

The two unmerged proposals were shaped as survey material. Their authors wanted comparative judgment, not integration. The maintainer initially encountered them as contributions. Once those purposes diverged, even useful review became waste from the project's point of view.

This suggests a definition of machine-speed work that is more demanding than fast code generation. A machine-speed pull request should be cheap to understand, not merely cheap to open.

It should state the behavior it intends to change. It should keep the change as small as the claim allows. It should carry tests that fail for the old behavior and pass for the new one, where such tests are possible. It should identify what generated it and what checked it. It should expose uncertainty instead of filling the description with confidence. It should have an owner capable of responding to review. It should be reversible when the evidence is incomplete.

These requirements may reduce the number of pull requests a system can produce. That is not a loss if proposals were never the scarce outcome.

Some organizations will try to solve the review queue by asking agents to argue with one another until they reach agreement. A generator writes the patch. A reviewer comments. The generator revises. A testing agent expands the suite. Another agent ranks the risks. This can be powerful. It can also create a closed epistemic loop: a great deal of activity based on a shared misunderstanding, delivered to the human as consensus.

The human should not be required to replay every internal step. That would eliminate the benefit. But the final package needs evidence that escapes the loop. Execution against independent tests. Comparison with a specification the generator did not invent. Evaluation on historical failures. Review by the owner of the affected system. Observation after a limited release. The more production is automated, the more valuable such contact with an external constraint becomes.

This is proof-carrying work in an early, practical form. The phrase does not mean mathematical certainty. It means that the artifact arrives with the reasons an institution should spend less attention on it and with clear limits on those reasons. The proof is proportional to consequence.

A spelling correction needs little ceremony. A dependency upgrade affecting authentication needs more. A generated migration that can destroy data should not earn trust from a beautiful summary. The review budget should follow the possible damage, novelty, irreversibility, and reach of the change—not the fluency of its author or the speed with which it appeared.

There is a cultural change hidden inside this design. Developers have often treated review as service to the author: help improve my patch, unblock my work, tell me what to fix. In a high-production system, review is also allocation. The reviewer decides which proposed changes deserve to consume the finite capacity of the codebase and its maintainers.

Declining a plausible change can be productive. Requesting a smaller one can be productive. Closing a pull request that cannot answer questions can be productive. These actions protect the future reader who will meet the code during an incident, when the original explanation is gone and the system is behaving badly.

That future reader is part of the review budget too. A clever generated abstraction may save twenty lines today and charge hours of comprehension to people who did not request it. Code is read more often than it is written; machine generation can increase that imbalance. The cost does not vanish. It moves from the moment of authorship into maintenance.

The merge button is therefore less like a publication button than a promise. The project promises to build on the change, explain it, repair it, and carry it through future versions. The person who presses the button is not certifying that every token passed through a human mind. The person is saying that the available evidence and the shape of the change justify that continuing obligation.

Software at least offers unusually direct checks. It can compile. Tests can run. Behavior can be observed. A bad change can often be reverted. The repository preserves an artifact trail showing who proposed what, which checks passed, what reviewers asked, and when authority was exercised.

Other knowledge systems have weaker boundaries. A scientific claim can be restated in a review article, compressed into an abstract, cited in an introduction, and repeated in a grant application without encountering an executable test. Each appearance can look like another piece of support even when they all point back to the same uncertain observation.

The pull request has a merge button. The literature has a citation.
