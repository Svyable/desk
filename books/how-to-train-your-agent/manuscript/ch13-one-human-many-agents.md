# One Human, Many Agents

The first agent tends to become everything.

It researches, writes, schedules, remembers, checks, buys, summarizes, codes, and keeps track of loose ends. The attraction is obvious. One interface, one relationship, one place to ask. The agent starts to resemble the universal assistant computing has promised for decades.

Then the jobs begin to interfere with one another.

The writing preferences that make a good editor are irrelevant to expense reconciliation. The broad web access useful for research is unnecessary for a private family calendar. The permission to modify code has no reason to sit beside purchasing authority. A memory that helps with one client may be inappropriate for another.

The universal assistant becomes an organization without departments.

That can work for a while.

It becomes harder as consequence grows.

Human institutions specialize because different work benefits from different knowledge, tools, incentives, permissions, and standards. Specialization creates coordination cost, which is why organizations also spend enormous energy trying to reduce handoffs. Agents inherit the same tradeoff.

One general agent has low coordination cost and broad context.

Several specialized agents can have cleaner jobs and safer boundaries.

Neither arrangement is automatically better.

The principal's task is to decide when the work has earned a division of labor.

This is another place where the technology's spectacle can mislead. Multi-agent systems sound advanced. An orchestrator delegates to researchers, coders, critics, planners, and reviewers. The diagram resembles a company in miniature. The temptation is to assume that more agents mean more intelligence.

Often they mean more messages.

Anthropic's engineering guidance has warned against unnecessary agent complexity and described orchestrator-worker patterns as useful when tasks genuinely decompose. OpenAI has similarly advised starting with a single agent and introducing multi-agent designs when they are needed. The advice is not anti-ambition. It recognizes that coordination has a cost even when the workers are software.

Every handoff can lose information.

Every additional agent can introduce another interpretation of the goal.

Every shared memory can widen privacy exposure.

Every specialized role needs evaluation.

Every delegation creates a question of which output the principal should trust when two agents disagree.

Parallel labor is cheap.

Coherence is not.

The right reason to create a second agent is therefore not that the first one is busy. Software can often run more instances of the same role. The better reason is that the work has a stable distinction worth preserving.

A research agent and an editor may deserve separation because one should search broadly while the other should judge the manuscript against a narrow voice and evidence standard.

A household logistics agent and a financial agent may deserve separation because their data permissions should differ.

A coding agent and a deployment agent may deserve separation because writing a change and authorizing production are different authority levels.

A sales-research agent and a customer-communication agent may deserve separation because the first can explore speculation that the second should never send.

Specialization earns its keep when it creates a meaningful difference in purpose, context, tools, permissions, or evaluation.

If the distinction exists only in the name, you have built a costume department.

This is why people should resist naming five agents before they have trained one role well. It feels productive to create a “team.” The principal writes biographies, assigns personalities, and imagines a tiny digital company. The system can become a role-playing exercise that produces more orchestration than outcome.

The unit of design should remain the job.

What recurring work exists?

What evidence tells us it is done?

What context does it need?

What authority does it require?

Only then ask whether another role should own it.

This keeps the organization grounded in consequence.

A second agent can solve a problem the first agent creates: conflict of function.

Consider an agent trained to produce persuasive sales proposals. It learns to present the product strongly, select supporting evidence, and maintain momentum. You also want the system to review proposals for unsupported claims and contractual risk.

The same model can perform both tasks sequentially. But separating the roles can help because the evaluation criteria differ. The producer is rewarded for persuasive completeness. The reviewer is rewarded for finding reasons the producer should not send.

The separation creates institutional friction on purpose.

Human systems do this everywhere. The person spending money is not always the person reconciling it. The developer does not always approve her own change. The prosecutor is not the judge. The author is not the copy editor. Separation of function can protect against one objective consuming the whole process.

Agents make such separation cheap enough to use in smaller settings.

A freelancer can afford a critic.

A household can afford a checker.

A one-person company can create an internal adversary before sending consequential work into the world.

This does not guarantee independence. Two agents powered by the same model, context, and assumptions may reproduce the same error with different role labels. The reviewer can become a rubber stamp in software just as in human organizations.

Real independence requires some difference in information, objective, method, or evidence.

A fact-checking agent might be restricted to primary sources and asked to challenge claims without seeing the author's preferred conclusion. A code reviewer may run separate tests. A purchasing reviewer may compare the proposed transaction with policy rather than merely rereading the recommendation.

The role separation should change what can be known or rewarded.

Otherwise it is theater.

Several agents also change the principal's work.

With one agent, the human has a conversation.

With many, the human has a queue.

Tasks complete in parallel. Questions arrive. Two agents need the same file. One waits for another. A third discovers that the original objective was ambiguous. The principal who wanted less coordination can become the scheduler of a tiny bureaucracy.

This is where many-agent enthusiasm meets attention economics.

The bottleneck moves upward.

Imagine a designer with four digital roles: research, production, copy, and client administration. Each saves time independently. Together they can produce more work than the designer can review. Research generates opportunities faster than production can absorb them. Production creates options faster than the human can choose. Administration sends approval requests while the designer is trying to make a creative decision.

The system has increased throughput and decreased peace.

A trained portfolio therefore needs cadence.

Not every agent should interrupt the human whenever it finishes something. Some work can flow to another role. Some can wait for a review window. Some can be sampled. Some should surface only exceptions. Some genuinely deserve immediate attention.

The principal becomes a designer of queues.

This sounds bureaucratic because it is a small version of operations management. Once a person has parallel delegated labor, coordination problems that once belonged to companies arrive on the desktop.

Which work is urgent?

Which work blocks other work?

Which decisions require the principal?

Which outputs can be automatically verified?

Which tasks should be killed because the organization is producing more possibilities than it can use?

The last question is easy to overlook.

Agents make starting work almost free. This can create a glut of unfinished intelligence.

Research every market.

Draft every idea.

Generate ten designs.

Explore five architectures.

Ask three agents to critique the plan.

The machine has no natural sense of opportunity cost unless the principal creates one. It can pursue every branch because compute is cheaper than human attention.

The principal still has one life.

A many-agent system therefore needs scarcity imposed from above.

Which question matters enough to deserve parallel labor?

Which result will change a decision?

How many alternatives can the human meaningfully evaluate?

What should not be started?

Management becomes less about activating capacity and more about refusing it.

This may be one of the stranger features of the agent economy. For generations, managers were constrained by the cost of labor. Headcount had to be justified. People could not be assigned casually because salaries, calendars, morale, and hiring created friction.

Digital labor removes much of that friction.

Bad projects can now receive staff.

The one-person company can afford to waste a whole department's worth of machine effort on an idea that should have died in ten minutes.

Compute cost will restrain some uses, especially at scale. But for many knowledge tasks the more important scarce resource will be the principal's ability to tell good branches from pointless ones.

The agent portfolio should therefore be trained not only to do work but to compete for attention.

A research role can say, “I found no evidence that would change the decision; stop here.”

A production role can return one recommended option and two meaningful alternatives instead of twenty variations.

A monitoring role can remain silent when nothing changed.

A critic can distinguish a fatal objection from a cosmetic preference.

The best digital employees may be notable for how little they put in the principal's inbox.

Specialization also raises the question of shared memory.

Should every agent know what every other agent knows?

The convenience argument says yes. A common memory prevents repetition. The research agent discovers a customer preference, and the writing agent can use it. The scheduling agent knows a trip has been booked. The finance agent knows the renewal was canceled.

The governance argument says not so fast.

Shared memory can create contamination. A speculative research note becomes treated as fact by another role. Confidential information crosses a boundary. An obsolete decision propagates. One compromised agent gains indirect influence over others through the shared context.

The solution is not necessarily isolated silos. It is structured sharing.

Some facts belong in common sources of record.

The current project status.

Approved customer preferences.

Final decisions.

Published policy.

Other information should remain role-local.

Draft hypotheses.

Private notes.

Sensitive personnel data.

Unverified web findings.

The principal needs to decide what qualifies for promotion into shared institutional memory.

This is analogous to a company where not every Slack message becomes policy and not every employee gets every folder.

Many-agent systems make information architecture part of personal productivity.

There is another trap: agent-to-agent consensus.

If three agents agree, the output can feel more trustworthy. Sometimes independent agreement is useful. But three copies of the same model given the same evidence may not constitute three independent judgments. They can share blind spots and training biases. Even different models may converge because they rely on the same flawed source.

The principal should ask what makes the second opinion genuinely second.

Different evidence?

Different objective?

Different method?

Different model?

An external deterministic check?

A human specialist?

The count of agents is less important than the diversity of error.

This is where a portfolio can become sophisticated without becoming crowded. One producer. One checker. One deterministic test. A human at the right boundary.

The system may outperform a swarm of eight agents debating one another in beautifully formatted prose.

The point is not to recreate the org chart you already know.

It is to build the smallest institution that makes the delegated work dependable.

Sometimes that institution is one agent and a good evaluation suite.

Sometimes it is a pair with intentionally opposed roles.

Sometimes it is a group of specialized workers coordinated by another agent.

Sometimes the correct answer is ordinary software because the task does not need interpretation at all.

The agent economy will tempt us to use agents for problems databases, scripts, checklists, and rules already solve better.

A smart principal is not loyal to intelligence.

She is loyal to the result.

This principle keeps the many-agent system from becoming a hobby.

Every new role should buy something observable: safer permissions, better specialization, independent review, lower context contamination, faster parallel work, or clearer accountability.

If it buys only the pleasure of having a digital team, keep the single agent.

There is a social effect worth noticing too. People may begin talking about “my agents” the way executives talk about teams. The phrase can become status. One person has a researcher, analyst, scheduler, editor, coder, and shopper running in parallel.

The impressive number will not matter for long.

The useful number will be how much reliable consequence one person can direct without becoming the bottleneck or the casualty.

A person with twenty poorly trained agents may be less capable than one with two excellent roles.

The first has capacity.

The second has an institution.

This is why the book keeps returning to training. Multiplication before training multiplies variance, permissions, context, and supervision. Training before multiplication creates a template that can be specialized deliberately.

The first agent teaches you how you manage.

The second teaches you whether your management scales.

By the fifth, the central question is no longer whether the machines can work in parallel.

It is whether you can still tell which work deserves to exist.
