# Failure Cascades

Knight Capital did not need a malicious superintelligence to lose control of an automated system.

In the summer of 2012, the firm prepared software for a new New York Stock Exchange program. Code was deployed across servers, but one of eight servers did not receive the new version. Old code remained callable. On August 1, incoming orders triggered the defective behavior on that server, which sent orders rapidly into the market. The problem accumulated at machine speed. The firm suffered an enormous loss in less than an hour and required rescue financing soon afterward.

The Securities and Exchange Commission’s later order described not only the coding history but failures of deployment procedure, review, controls, and safeguards. The event is useful because it punctures a fantasy: complex technological failures are usually not one mistake. They are chains of ordinary weaknesses that align.

Artificial intelligence will create new links in such chains.

A model misunderstands an instruction. A tool has broader permissions than expected. A monitoring system summarizes away the anomaly. A human reviewer is overloaded. An agent retries after failure. Another system interprets the retries as demand. An automated response changes the environment, causing the original model to receive new evidence that appears to confirm its assumption.

No component needs to be wildly incompetent. Interaction is enough.

This is why intelligence allocation has to be studied as a system property. Benchmark accuracy of the model tells us little about cascade risk if the model sits inside feedback loops.

Feedback turns outputs into future inputs.

Markets are a clear example. Trading algorithms react to prices partly created by other algorithms. Social platforms recommend content, users respond, and the responses train future recommendations. Navigation systems route drivers away from congestion and can create congestion elsewhere. Pricing agents observe competitor prices that may themselves be generated by agents.

When many systems learn from one another, causality becomes circular.

The 2010 Flash Crash is often invoked as a parable of algorithmic markets. The joint CFTC-SEC report documented an extraordinary sequence in which prices moved violently and liquidity conditions changed rapidly. The specific event had specific causes and should not be reduced to “robots panicked.” The broader design lesson is that fast interacting systems can produce collective behavior that cannot be inferred from any one component’s intention.

AI agents will create similar interaction domains outside finance.

Imagine procurement agents negotiating with supplier agents. Pricing agents adjusting against competitors. Recruiting agents screening candidates whose application agents optimize for the screeners. Content agents writing for ranking agents. Cybersecurity agents probing and defending continuously. Personal assistants scheduling against other assistants.

The environment becomes populated by policies adapting to policies.

This changes risk. A system tested against human behavior may behave differently when most counterparties are automated. Small timing or objective changes can produce new equilibria. The system needs monitoring at the ecosystem level.

Cascades often exploit homogeneity.

If many organizations rely on the same model, a shared error can synchronize decisions. A flawed vulnerability assessment could cause many systems to apply the same bad patch. A mistaken economic interpretation could influence thousands of trading or procurement agents. A model update could alter customer-service behavior across an industry overnight.

Diversity becomes systemic insurance.

This does not mean every organization should build its own model. It means critical systems should understand common dependencies and create breakpoints: independent verification, staggered updates, canary deployment, multiple providers, local fallback, and human review of unusual collective behavior.

Staggering is underappreciated.

Software culture celebrates rapid global deployment because consistency is easier. But simultaneous change creates simultaneous exposure. A staged rollout lets reality test the change on a smaller surface. If the update is bad, fewer systems are affected and the signal appears before full propagation.

AI model updates should often be treated like infrastructure changes rather than app cosmetics.

A new model can alter wording, tool selection, refusal behavior, coding style, risk tolerance, and interaction with prompts. Even if average evaluation improves, rare behaviors may shift. Organizations whose agents have significant authority should know when the underlying model changes and should be able to hold, test, or roll back.

Cascades also exploit hidden coupling.

Two systems that appear independent may share a database, identity provider, cloud region, model API, or vendor. An outage in the shared dependency becomes a multi-system failure. This is familiar in cloud computing, where a single service incident can affect many unrelated brands that users imagine as separate.

Cognitive infrastructure will create even deeper coupling because the same model may sit inside decisions across sectors.

Dependency maps should therefore include cognition. Which essential processes rely on which model, provider, retrieval store, network, or agent framework? What happens if that component returns wrong answers rather than no answers? Silent degradation is more dangerous than outage because it can continue producing plausible behavior.

Resilience planning tends to focus on availability. AI requires integrity resilience too.

Can the organization detect when the system is available but untrustworthy? Can it compare outputs against baseline behavior? Can it route critical tasks to another method? Can it narrow permissions while diagnosis occurs?

This is the cognitive equivalent of operating on backup instruments.

Cascades are not always technical. Organizational behavior can amplify them.

A model flags a risk. Managers act defensively. Their actions create new signals that other models interpret as confirmation. For example, automated credit tightening during an economic shock could reduce lending, worsening conditions and causing further risk scores to deteriorate. Similar procyclical dynamics already exist in financial systems. AI can speed and personalize them.

Policy must sometimes allocate intelligence against the local objective.

A bank’s risk model may rationally reduce exposure while a regulator worries about system-wide credit contraction. A hospital may optimize bed use while a public-health authority preserves surge capacity. A delivery firm may optimize routes while a city manages congestion. Local intelligence and global intelligence can point in different directions.

This is why institutions exist above individual optimizers.

Cascades also arise from escalation. If agents are designed to send uncertain cases to humans, a shared shock can create a flood of uncertainty. The human fallback queue collapses. Under pressure, reviewers approve faster, exactly when scrutiny is most needed.

Fallback capacity must be designed for correlated exceptions.

One method is graceful degradation: when load rises, the system narrows service rather than preserving full functionality poorly. A hospital moves into disaster protocols. A website disables expensive features. A financial system reduces position limits. An AI service can switch critical tasks to conservative modes and defer low-priority work.

The key is deciding degradation policy before the overload.

During a crisis, every stakeholder believes their task is critical. Precommitted service tiers prevent the queue from becoming political chaos.

Failure cascades also reveal the value of circuit breakers.

A circuit breaker interrupts propagation when behavior crosses a threshold. Financial markets use trading halts. Electrical systems isolate faults. Networks rate-limit. Factories stop lines. The common logic is to sacrifice local continuity to preserve the larger system.

AI agents need circuit breakers at several levels. Per-action limits. Per-user limits. Per-agent budgets. Cross-system anomaly detection. Emergency revocation of credentials. Global pauses for a model version. External safety constraints that the agent cannot negotiate away.

The breaker should be simpler than the system it stops.

If the kill switch depends on the same model infrastructure that is failing, it is not a kill switch. If emergency authorization requires the system being disabled to approve the request, the control is circular. Simplicity and independence matter most at the boundary of failure.

The human equivalent is command clarity. During a serious incident, someone must have authority to stop activity even when the organization does not fully understand the cause. This authority can be abused, but ambiguity is worse under speed.

NASA mission control, aviation command, emergency medicine, and incident response all recognize the need for defined operational authority. Debate can resume after the immediate hazard is contained.

Cascades challenge cultures that punish false alarms. If stopping the system is expensive and every stop is treated as failure, people hesitate. Then the first stop occurs late.

Safety cultures need tolerance for some unnecessary interruption.

The exact rate is a policy question. Too many stops destroy productivity. Too few permit catastrophe. The organization should measure near misses and learn whether thresholds are calibrated rather than rewarding uninterrupted operation as a sign of perfection.

Near misses are valuable because they reveal pathways before the full consequence arrives.

AI can help mine near misses from logs: attempted actions blocked by permissions, model disagreements, user overrides, repeated retries, unusual tool sequences, sudden confidence changes. These events form a leading indicator of cascade risk.

But only if they are retained and reviewed.

The deeper challenge is epistemic. Complex systems make it hard to identify one root cause. Organizations prefer a root cause because it promises closure: fix the bug, retrain the worker, update the prompt. Cascades often have multiple necessary conditions. Remove one and the incident might not recur, but another path remains.

Postmortems should therefore ask not only “what failed?” but “what allowed this failure to propagate?”

Propagation is the allocation question.

Why did one model have authority across so many accounts? Why did one bad deployment reach every server? Why did the alert fail to interrupt? Why did retries amplify load? Why did every verifier share the same data source? Why was there no safe state?

These questions turn accidents into architecture.

The age of AI will contain spectacular failures because every technological age does. The quality of our institutions will be visible not in whether failure disappears but in whether failures remain bounded, legible, recoverable, and educational.

Intelligence should make the system easier to stop before it makes the system faster to run.
