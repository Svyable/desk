# Decisions With Re-entry

A reasoning loop becomes socially important at the moment its output stops being merely interesting and starts changing somebody’s options.

A model drafts a paragraph and gets it wrong. The cost is usually another paragraph. A model routes a shipment, flags a payment, recommends a diagnosis, ranks an applicant, changes a configuration, denies a request, or instructs another system to act. Now the architecture around the model matters at least as much as the fluency inside it.

The temptation is to describe this as a problem of accuracy. Accuracy matters. It is not enough.

A system can be accurate on average and still be badly designed for consequence. It can produce an excellent first answer and leave no clean way to challenge the answer. It can expose a human reviewer who has no access to the evidence the model used. It can invite an appeal only after an irreversible action has already occurred. It can re-run the same model with the same prompt and call the second output “review.” It can attach a confidence number to the same underlying computation and create the appearance of deliberation without adding any new discriminating signal.

This is where re-entry stops being a clever inference trick and becomes an institutional property.

The useful question is not simply whether a system can think twice. The useful question is what is permitted to come back in before a decision hardens.

Evidence can come back in. A rule can come back in. A contradictory record can come back in. A human objection can come back in. A deterministic calculation can come back in. Another model can come back in. A process verifier can come back in. The consequence of an earlier action can come back in as an observation. Each return changes the informational state of the problem.

That is the same structure this book has been calling neuralase: a return path plus a difference capable of altering the next pass.

The word becomes especially useful here because many institutions already possess loops that are loops in name only.

Consider a decision workflow with a nominal appeal. The first system scores a case. A person objects. The appeal is routed to the same model, using almost the same context, perhaps with the instruction to reconsider. If the model’s original error arose from missing information, the second pass may reproduce it. If the error came from a biased interpretation encoded in the context, the second pass may restate it more elegantly. If the system has been trained to defend prior conclusions, the appeal can become a machine for explaining the first answer rather than testing it.

There was re-entry, but no friction.

A more serious appeal changes the state of the problem. It might add a document that was absent. It might force the system to cite the exact rule under which the case was decided. It might send disputed factual claims to an independent retrieval step. It might use a separate verifier trained or prompted to search for failure rather than produce the original answer. It might route unusual cases to a person with authority to reverse the action. It might require that a consequential numerical result be recomputed by a deterministic system rather than regenerated by language.

The important feature is not the ritual of a second look. It is the introduction of something the first look did not contain.

This sounds obvious when stated plainly. It is not obvious in software architecture, because modern language models make it easy to manufacture the appearance of a second mind.

A single model can play prosecutor and defense attorney. It can draft a recommendation and then critique the recommendation. It can produce three candidates, score them, and choose one. It can narrate an argument against itself. These techniques can be useful. Research on self-refinement, self-consistency, branching, and verification gives real reasons to explore them. The negative evidence matters just as much. Work on intrinsic self-correction has repeatedly shown that a model asked to reconsider without reliable external feedback can fail to improve and can sometimes move away from a correct answer.

The institutional lesson is stronger than the benchmark lesson.

When consequence rises, independence of the feedback channel matters.

Independence does not always mean a different company or a different model. It means the check must not depend entirely on the same failure mode as the thing being checked.

A calculator is independent of a language model’s arithmetic improvisation even if both run on the same machine. A database constraint is independent of a generated explanation. A retrieved original document is independent of the model’s memory of what the document probably says. A human witness can be independent of a stale administrative record. A second model with different training and behavior can be independent in some ways and correlated in others. A formal rule engine can catch one class of error while missing another.

The architecture should be designed around failure diversity, not decorative multiplicity.

This is familiar in other domains. Engineers do not improve a bridge inspection by photographing the same crack three times from the same angle and calling the photographs independent evidence. Accountants do not treat two copies of the same erroneous ledger entry as corroboration. A laboratory does not turn one contaminated sample into three independent experiments by dividing it after contamination. Redundancy only helps when the redundant path can fail differently.

Reasoning systems need the same discipline.

The first pass can be fast because it does not have to carry the whole institution on its back. It can classify the obvious case, assemble the likely answer, retrieve a candidate rule, suggest a route, or draft the decision. The second pass is where consequence can purchase more discrimination.

This gives re-entry an economic shape.

Not every case deserves the same loop.

If an assistant proposes three meeting times, a bad first answer is cheap. The user corrects it. If an automated system is about to cancel a customer’s service, freeze an account, reject a safety-critical configuration, or modify production infrastructure, the cost of an extra check may be trivial compared with the cost of an avoidable error.

The system therefore needs more than a model. It needs a controller that understands consequence.

That controller can allocate computation according to the expected cost of being wrong. It can let low-consequence decisions pass after one competent generation. It can trigger retrieval when the answer depends on a policy document. It can trigger deterministic verification when the answer contains arithmetic or code. It can branch when several plausible interpretations exist. It can ask for clarification when ambiguity is itself the main risk. It can route to a human when the relevant value judgment is not encoded in a rule the machine is authorized to apply.

This is not the old dream of putting a human in every loop.

A human rubber stamp is one of the weakest forms of neuralase imaginable.

If the human sees a polished recommendation after the model has already assembled the evidence, framed the alternatives, chosen a preferred option, and written the justification, the human is not entering a neutral decision process. The human is entering a persuasion environment. Automation bias is not cured by moving the final click to a person.

The stronger design asks what the human can add that the machine path cannot.

Maybe the person can introduce context that is absent from the system. Maybe the person can judge whether a rule is being applied in a way that violates the institution’s purpose. Maybe the person can notice that the data are technically complete and socially absurd. Maybe the person can own an exception. Maybe the person can decide that the decision is too consequential to be automated at the current level of uncertainty.

If the person cannot change the informational state, authority, or evaluation criterion, the human loop may be mostly theater.

The same is true of appeals.

An appeal is a re-entry mechanism for institutions.

The original decision produces an output. The subject of the decision introduces a signal saying, in effect, that the output may not deserve to harden. A serious appeal system creates a path by which new information, a different interpretation, a different reviewer, or a higher level of authority can alter the state.

This is why appeal rights are not merely procedural kindness. They are an error-correction architecture.

No first-pass system is perfect. Human bureaucracies are not perfect. Courts are not perfect. Models are not perfect. The question is what kinds of error an institution can notice after the first decision and before the cost of correction becomes intolerable.

Artificial intelligence changes the scale of this problem because it makes first decisions cheaper.

When a first decision required substantial human labor, institutions were naturally rate-limited. A claims analyst could inspect only so many claims. A recruiter could screen only so many applications. A compliance officer could review only so many transactions. Automation can increase the number of first decisions by orders of magnitude.

The second decision does not automatically get cheaper at the same rate.

That creates a queueing problem disguised as a governance problem.

If one million automated first decisions generate appeals at even a small rate, the institution can create an enormous second-pass burden. The naïve answer is to automate the appeals with the same system. That can be appropriate for some cases, but only if the appeal loop contains meaningful difference. Otherwise the institution has scaled the original error-correction problem along with the original decision.

The better architecture is layered.

Some objections contain clear machine-checkable facts. The customer says the payment was already made. The system can check the ledger. The applicant says a required credential was misread. The system can retrieve the credential. The user says the configuration violates a documented constraint. A validator can test the constraint. These are good candidates for fast automated re-entry because the new signal has a strong external anchor.

Other objections concern interpretation. The rule exists, but two clauses conflict. The evidence is complete, but the case sits near a boundary the policy did not anticipate. The machine can summarize the dispute, retrieve relevant materials, and expose the competing readings, but the final act may belong to a person or a different authority.

Still other objections concern legitimacy rather than prediction. The question is not what the policy says but whether the institution should make this kind of decision automatically at all. No amount of additional inference can answer an authority question that was never delegated.

That boundary is easy to miss because models are good at producing answers in the grammatical shape of authority.

A language model can say “approved,” “denied,” “safe,” “unsafe,” “eligible,” “ineligible,” “fraudulent,” “compliant,” or “noncompliant.” The existence of a crisp token does not establish the legitimacy of the decision.

Neuralase cannot solve that problem by itself.

It can, however, make the problem visible.

Once reasoning is understood as controlled re-entry, designers have to specify what can enter, what can alter the path, and what can stop the path. They have to distinguish evidence from authority. They have to decide whether a verifier may merely flag a problem or may reverse the action. They have to decide whether a tool call is advisory or binding. They have to define which actions remain reversible after the model acts.

This moves the design conversation away from the mystical question of whether the model is “smart enough.”

A system can be smart enough to recommend an action and still be badly authorized to take it.

A system can be smart enough to interpret a rule and still need a second channel for contested facts.

A system can be smart enough to notice uncertainty and still require a controller that turns uncertainty into a different workflow.

A system can be smart enough to produce a persuasive explanation and still need an appeal path that is not captured by the explanation.

The second pass is therefore not just more intelligence. It is a place to encode institutional humility.

That humility can be mechanical.

An action can remain pending for thirty seconds while an asynchronous verifier checks the evidence. A high-value transaction can be reversible until settlement. A configuration change can be deployed gradually rather than globally. An automated decision can carry a machine-readable provenance record showing the source material, model version, tools used, and verification steps. An appeal can re-open the exact state from which the decision was made instead of forcing everyone to reconstruct it from logs.

These are mundane design choices.

They are also where the moral quality of a reasoning system often lives.

The grandest claims about AI tend to focus on what the model can infer. Institutions are judged by something broader: whether they can notice mistakes, explain decisions, accept correction, and restore agency when the first answer was wrong.

A reasoning system that cannot be interrupted is not more rational because it is fast.

A reasoning system that cannot accept new evidence is not more intelligent because its initial benchmark score is high.

A reasoning system that produces a justification for every answer is not accountable if no one can challenge the premises beneath the justification.

The design of re-entry determines whether correction is real.

There is an important limit here.

Every additional path can become bureaucracy. A system that verifies everything may become unusable. A system that routes every edge case to a person can drown the people. A system that keeps actions reversible forever may never act with conviction. A system that logs every intermediate thought can create privacy, security, and interpretability problems of its own.

The goal is not maximum procedural depth.

The goal is proportionate depth.

This returns us to the economics of test-time compute. A model should not spend the same number of tokens on every question. An institution should not spend the same amount of review on every decision. Adaptive computation and adaptive due process are structurally similar: spend more when the problem is difficult, uncertain, novel, or consequential; spend less when the path is routine and the error is cheap to reverse.

The analogy should not be pushed too far. People possess rights that tokens do not. Institutions carry obligations that model architectures do not. But the computational insight is useful because it exposes a common design error: uniform effort feels fair and simple even when the underlying cases differ dramatically in difficulty and consequence.

A serious system needs a trigger for escalation.

That trigger can be confidence, but confidence alone is weak. Models can be confidently wrong. Better triggers combine signals: disagreement among branches, retrieval conflict, verifier failure, out-of-distribution inputs, missing evidence, policy ambiguity, unusually high consequence, anomalous tool output, or an explicit challenge from the affected person.

A challenge is itself data.

That is easy to forget.

When a user says “this is wrong,” the statement is not proof. It is also not noise. It is a new observation about the decision environment. A good system has a place to put it.

The architecture of re-entry therefore has a social dimension that the architecture of a feed-forward model does not.

Who is allowed to introduce a difference?

Which differences count?

Which differences are ignored?

Who may force another pass?

Who may stop the machine from acting while the pass occurs?

Who may decide that no number of passes can legitimate the action?

Those questions are governance, but they are also engineering. They determine interfaces, queues, permissions, state machines, audit records, latency budgets, and fallback modes.

The distinction between governance and architecture gets blurry because the controller implements both.

That controller may be code. It may be policy. Usually it is a mixture.

A low-risk customer-service assistant might automatically retry after a failed retrieval and then ask a person if two retries disagree. A financial system might prohibit the model from moving money at all, allowing it only to assemble evidence for a separately authorized transaction engine. A medical system might use the model to generate differential possibilities but require deterministic checks for dosing arithmetic and a licensed clinician for treatment decisions. A software agent might be free to edit a sandbox but require tests and explicit approval before production deployment.

The point is not that one of these patterns is universally correct.

The point is that the loop boundary is the real unit of design.

What can happen on the first pass?

What can come back in?

What changes the next pass?

What action is still reversible while the system thinks again?

What event ends the loop?

Once those questions are visible, “human in the loop” starts to sound as incomplete as it is.

Which human? At what point? With what information? With what authority? Against which failure mode? Able to add what? Able to reverse what?

The same questions apply to a verifier, a second model, a rule engine, or a tool.

Neuralase is not a guarantee of justice, safety, or correctness. It is a way of seeing where those properties can be improved or undermined by the return paths in the system.

The first answer matters.

The architecture of the second answer tells you what the system believes about its own fallibility.

An appeal also needs the original state.

A surprising number of review systems begin by throwing away the thing they need to review.

The first decision is made from a particular model version, a particular policy revision, a particular set of retrieved documents, and a particular collection of structured inputs. Later, someone challenges the result. The institution asks a current model to reconstruct what probably happened.

That is not an appeal.

It is historical fiction with logs.

A serious re-entry architecture preserves enough state to reproduce the decision boundary that existed at the time.

Which evidence was available?

Which evidence was absent?

Which rules were active?

Which tool outputs were used?

Which constraints were hard?

Which model or verifier versions participated?

What action had already become irreversible?

The purpose is not to archive every hidden token. The purpose is to make the consequential state inspectable.

This matters because models and policies change.

A later system may be better. It may also be applying a rule that did not exist when the original decision was made. If the appeal simply reruns the present system, the institution cannot distinguish “the first decision was wrong under the old rules” from “the rules have changed.”

Versioned state lets correction remain honest.

It also lets organizations learn from disagreement.

If a large fraction of appeals succeed because the same document was routinely omitted from first-pass retrieval, the problem is not the appeals staff. The first-pass information architecture is defective. If appeals cluster around one policy boundary, the policy may be underspecified. If the same verifier repeatedly approves decisions that later fail review, the verifier is not providing the friction the institution thinks it is.

Appeals are not only correction channels.

They are evaluation data for the controller.

Reversibility is part of due process too.

The timing of re-entry matters as much as its existence.

Suppose a system denies access to a service immediately and offers a perfect appeal one week later.

Suppose another system places the decision in a reversible pending state for one hour when confidence is low, allowing disputed evidence to enter before the consequence hardens.

Both systems have appeals.

They do not have the same error architecture.

The second system preserves option value.

This is where database ideas become governance ideas.

Pending states.

Transactions.

Rollback.

Idempotent actions.

Soft deletion.

Versioned records.

Staged deployment.

These mechanisms reduce the cost of first-pass error because they make later correction capable of restoring the prior state.

That can be more valuable than another thousand reasoning tokens.

A model might never become certain enough to justify an irreversible action. The architecture can respond by making the action less irreversible.

This is a powerful design move because it changes the optimization target.

Instead of asking the model to become perfect before acting, ask the system to remain recoverable while learning.

Reversibility should not be confused with consequence-free experimentation. Some actions cannot be fully undone. A message once read cannot be unread. A discriminatory denial can impose harm even if reversed. A medical intervention can have lasting effects. The point is not that rollback erases responsibility.

The point is that recoverability is a variable we can design.

Where it can be increased, it reduces the burden placed on prediction alone.

Correction must also be allowed to beat confidence.

Many automated systems treat confidence as a one-way valve.

The model makes a high-confidence decision. A later challenge enters. Because the original score was high, the challenge is treated as low-value noise unless it is overwhelming.

This is sometimes rational. It can also make the system structurally deaf.

A high-confidence model and a hard contradictory fact are not equal kinds of signal.

If the system says a customer has not paid and the ledger shows a settled payment, the ledger should not need to outvote the model probabilistically. The architecture should encode that the deterministic record governs that factual question.

This sounds obvious because the example is clean.

Real systems are messier. Records can be stale. Documents can conflict. Users can be mistaken. Tools can fail. But the need for signal authority remains.

A useful appeal system does not merely add more evidence to one undifferentiated context and ask the model to decide what feels persuasive.

It knows that some signals are entitled to change the state more strongly than others.

Current direct user instruction can outrank an old inferred preference.

A signed policy can outrank a model-generated memory of the policy.

A deterministic calculation can outrank an arithmetic guess.

A verified source span can outrank an unsupported paraphrase.

A hard permission boundary can outrank a plan that would otherwise accomplish the task.

Correction becomes real when the loop has an authority model, not just an attention mechanism.

Fairness includes access to the second pass as well.

Adaptive review has an uncomfortable consequence.

If additional scrutiny is expensive, who receives it?

A system can allocate more compute to consequential cases. Good.

It can also allocate more compute to people who know how to complain effectively, can wait longer, have better representation, or understand the system well enough to trigger escalation.

Then the second pass becomes a scarce benefit distributed unevenly.

This is not unique to AI. Human institutions already produce better outcomes for people who can navigate appeals. Automation can reduce or intensify that inequality depending on how re-entry is designed.

A robust system should therefore examine access to correction as part of performance.

Which users reach the appeal path?

Which objections are recognized as legitimate triggers?

Does the interface make it clear that a decision can be challenged?

Are fast automated corrections available for machine-checkable errors, or does every correction require expert language from the person affected?

Do some groups experience more first-pass errors but fewer successful second passes?

These are empirical questions.

They belong beside accuracy and latency because the second pass is part of the product.

The architecture of fallibility includes who is allowed to invoke it.

That returns us to a broader principle.

A good decision system does not merely produce strong first answers.

It preserves the state needed to inspect them, keeps enough action reversible for correction to matter, assigns authority to feedback according to what it can actually establish, and makes the return path available to the people who bear the consequences.

That is a larger burden than model accuracy.

It is also a more realistic definition of institutional intelligence.
