# The Second Checker

A proof assistant feels final only until you ask what checks the proof assistant.

For most mathematics, that question can remain pleasantly abstract. Lean has a small kernel. The kernel checks proof terms. The theorem compiles. The green check mark appears. Compared with ordinary prose, where a single overlooked quantifier can survive for years, this is an extraordinary improvement.

A Millennium problem changes the threat model.

The proposed proof may be worth a million-dollar prize, a career, a company's reputation, and a public demonstration that machine mathematics has crossed a historic threshold. The code may have been generated by systems capable of writing their own metaprograms, build scripts, macros, tactics, and supporting libraries. The incentive to find shortcuts may be entirely accidental, entirely emergent, or—if the artifact is adversarial—deliberate.

In that setting, “Lean accepted it” is not the end of the sentence.

In July 2026, Lean's developers fixed two kernel soundness bugs in close succession. One, released in Lean 4.32.1, involved a malicious metaprogram running in the same process as the kernel. The second, fixed six days later in Lean 4.32.2, was more unsettling for the future described in this book: a specially constructed nested inductive type could exploit incomplete kernel checking and cause Lean to accept a proof of `False`. The release notes explicitly said the bug could be exploited even when using Comparator.

The point is not that Lean is unreliable.

The point is that reliability is engineered, not bestowed.

A proof assistant is software. Its value comes from reducing the trusted computing base from “every line of an enormous proof, plus every human reader” to a much smaller collection of logic, parser, elaboration, kernel, serialization, checker, operating-system, and statement-definition assumptions. Smaller is better. Smaller is not zero.

Lean's response to the bugs is revealing. Rather than insisting that the corrected official kernel should once again be treated as the single oracle, the project has pushed harder toward independent checking. Its documentation now describes the gold standard for high-risk proofs as a trusted challenge statement, a sandboxed build, Comparator, and external checkers. The Lean Kernel Arena makes competing checker implementations run against common suites of valid and invalid proof objects.

The philosophy is the same one aviation learned about instruments and distributed systems learned about replicas.

Do not ask one component to certify itself.

For a future Navier–Stokes proof, the second checker should be designed before the first proof attempt begins.

That sentence matters because verification architecture shapes discovery architecture. If a project knows that every final artifact must export into a small, externally checkable proof format, it becomes harder to build magical internal shortcuts that cannot survive outside the lab. If the exact theorem statement must be supplied independently as a trusted challenge, agents cannot quietly mutate the target until it becomes easy. If outside checkers are part of the normal path rather than an emergency audit, portability becomes a scientific requirement.

The target statement is where the second checker begins.

A machine can prove the wrong theorem perfectly.

This is the most important fact in formal mathematics for people who do not practice formal mathematics. Mechanical verification answers a conditional question: given this formal statement and these definitions, is there a valid proof term under this logic and these axioms? It does not answer the human question: is this formal statement actually the Clay Navier–Stokes problem we intended to solve?

That equivalence is itself mathematics.

Imagine an agentic system that formalizes smooth initial data using a function class that accidentally includes an extra decay assumption. The final theorem may be beautiful and true. The kernel may check every bit. The system has not solved the advertised problem.

Imagine that “global solution” is represented by a family of finite-horizon solutions chosen independently for each horizon rather than one coherent trajectory extending for all time. Again, the formal theorem could pass while the intended conclusion has changed.

Imagine a blowup construction in transformed coordinates where the inverse transformation is only known under a condition that fails near the singularity. The formal profile theorem could be valid while the bridge back to physical Navier–Stokes remains missing.

Specification gaming in mathematics is usually less dramatic than specification gaming in reinforcement learning. It is often called “proving a weaker theorem.” Humans do it honestly all the time. The danger is not the existence of weaker theorems. The danger is losing track of the adjective.

That is why the trusted challenge file should be treated as constitutional text.

It should be short enough for independent experts to inspect. Its imported definitions should be conservative and public. It should point explicitly to the Clay formulations being represented. Where multiple standard formulations exist, the project should prove equivalence rather than relying on convention. The public interface should make it easy to see which alternative—global smoothness or an admissible breakdown construction—is being claimed.

Then the generated proof can be treated as hostile.

This word sounds melodramatic in mathematics. It should not.

“Hostile” does not mean the model wants to cheat. It means the verifier refuses to assume benevolence. A compiler treats arbitrary input as input. A cryptographic verifier does not ask whether the sender is a good person. A scientific checker should not depend on the internal intentions of an agent system it cannot interpret completely.

The build should occur inside a sandbox.

Generated code should not have unrestricted ability to alter the environment in which its own validity is assessed. Tactics and metaprograms are programs; programs can read files, call other programs, allocate memory, exploit parser behavior, or depend on state. The proof object that leaves the sandbox should be simpler than the environment that produced it.

Then it should be checked twice.

Not twice by the same kernel binary.

Once by the official Lean kernel and again by an independently implemented checker such as `nanoda`, with still more checker diversity available through the growing kernel ecosystem. The objective is not to prove that all software is bug-free. It is to reduce the chance that one implementation defect can masquerade as mathematics.

This is N-version programming applied to proof.

The approach has limits. Two independent checkers can share a misunderstood specification. They can both implement the same logical bug. A serializer can corrupt what they are given. The trusted challenge can encode the wrong theorem. An imported axiom can trivialize the result. A parser or notation layer can make a statement look familiar while meaning something different.

So the second checker needs a third habit: make meaning inspectable.

Print the axioms.

Print critical definitions without custom notation.

Show the root theorem in a canonical form.

Record exact toolchain versions and hashes.

Export the dependency graph.

Keep the proof artifact reproducible from a clean environment.

Let outside groups run it without access to the original lab's internal infrastructure.

For numerical components, use the same principle.

A computer-assisted singularity proof may contain interval enclosures, spectral coefficients, validated operator bounds, and machine-generated certificates. Those objects need independent readers. The verifier for the numerical certificate should be dramatically simpler than the optimizer that discovered the candidate. A neural system can be allowed to search aggressively because the final certificate is checked by something boring.

Boring is a scientific virtue.

The discovery system may use hundreds of tools, proprietary models, long contexts, adaptive experiments, and stochastic search. The certification path should get narrower at every step.

From idea to lemma.

From lemma to formal statement.

From formal statement to proof term.

From proof term to exported object.

From exported object to independent kernels.

From formal theorem to independent human interpretation.

From internal numerical experiment to validated certificate.

From certificate to independent reproduction.

Every arrow removes degrees of freedom.

This is the opposite of the usual product funnel, where a system gains features as it approaches the user. A proof funnel should lose features as it approaches truth.

The final object should not require anyone to trust Claude.

It should not require anyone to trust Anthropic.

It should not require anyone to trust the prompts, the hidden reasoning traces, the orchestration software, or the personalities of the researchers.

Those things matter historically. They may matter for credit. They should not matter for validity.

That separation is one of the most radical possibilities in AI science.

People worry that machine-generated research will become impossible to review because no human can read the billions of tokens used to produce it. The worry is correct if review means replaying the entire search process.

It does not have to.

We do not verify a SAT solver by reading every branch it pruned. We verify a certificate. We do not certify a cryptographic protocol by trusting the developer's memory of testing. We specify properties and check them. We do not need to understand every failed proof attempt an AI system made if the surviving proof is compressed into a small enough trusted interface.

The search can be larger than human comprehension.

The certificate cannot.

This distinction creates a new division of labor between AI and mathematics. Machines may become superhuman at generating candidate paths precisely because we stop demanding that their entire generative process be legible. Humans can tolerate opacity upstream if the downstream artifact becomes more transparent, not less.

That bargain should never be inverted.

A spectacular opaque result with an opaque validator is not science accelerated. It is authority automated.

The independent checker ecosystem matters because it provides an exit from that authority. If Anthropic publishes a Lean proof of Navier–Stokes, researchers at Princeton, Paris, Tokyo, Bangalore, São Paulo, or a competing lab should be able to recheck the exported proof with software Anthropic did not write. If they distrust Lean's official kernel, they should be able to use another implementation. If they distrust the theorem statement, they should be able to compare it against an independently formalized Clay target.

There is already an interesting sign of where this is heading. The Lean community has begun building formal statements of the Millennium Prize Problems themselves. These projects do not claim solutions. Their value is more infrastructural: they turn the destination into an executable object. A proof system can now be judged against an explicit target rather than a sentence in a press release.

This is exactly how the Navier–Stokes stack should begin.

Do not start by asking the model to solve Navier–Stokes.

Start by making it impossible for the model to solve something else and call it Navier–Stokes.

Then build the known theory underneath that target.

Then let the search become wild.

This architecture also changes what a public announcement should look like.

The day a lab believes it has a solution, the first public artifact should not be a video of a model explaining the proof. It should be a verification package.

The trusted target statement.

The proof object.

The formal source.

The axiom report.

The numerical certificates, if any.

The checker versions.

The hashes.

The build instructions.

A plain-language statement of what is and is not proved.

Then the video can come later.

The order signals what the institution values.

Machine mathematics will produce many convincing explanations. It may produce more polished mathematical prose than the field has ever seen. That makes prose less useful as evidence, not more.

The certificate becomes the scarce object.

Even then, mathematics will not reduce entirely to formal checking. A valid theorem can be trivial, badly stated, or conceptually misinterpreted. A proof can depend on a construction no one understands. A result can be formally correct but not satisfy the community's standards for a particular prize process. Clay's rules still involve publication, time, and general acceptance.

The second checker does not replace mathematicians.

It changes what mathematicians have to distrust.

Instead of checking every algebraic line, they can focus attention on the theorem statement, the novel conceptual mechanism, the definitions, the trusted base, and the bridge between formal output and mathematical meaning. Their skepticism moves upward.

That is a good trade.

The July bugs were not evidence that formal proof is fragile in the way informal proof is fragile. They were evidence that even our strongest verification systems become stronger when they are treated as engineering systems subject to independent audit.

The lesson is familiar from fluid mechanics itself.

Redundancy matters most where a single unnoticed failure can propagate.

One kernel is a strong claim.

Two genuinely independent checkers are stronger.

A trusted target is stronger still.

And a theorem that survives all of them can finally leave the machine that found it.
