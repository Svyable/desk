# The Commit as Evidence

A Git commit looks more official than it is.

It has an author. It has an email address. It has a date. It has a message. It points to a tree. It may have parents. Printed by `git log`, the whole thing resembles a durable entry in a technical ledger.

Most of those fields are claims.

Git does not require a passport before accepting an author name. It does not call an employer to verify an email address. It does not establish that the author personally typed the code. It does not prove that the committer reviewed the patch, understood it, or even saw every generated byte in the resulting tree.

A commit is extremely good evidence of some things and weak evidence of others.

Confusing those categories is becoming expensive.

Start with what Git's object model gives strongly.

A commit identifies a particular tree and a particular set of parent relationships. Its object name is derived from its contents under the repository's hash format. Change the tree, parent, author field, timestamp, message, or other hashed commit content and the object name changes. If you already trust a particular object ID, you can later detect that a different object is not the same commit.

This is integrity through identity.

It is not immutability.

A branch can be moved. A history can be rebased. A commit can be replaced by a different commit with a different object ID. A force push can make a server's branch name point somewhere new. Old objects may remain in some repositories for a while and disappear from others after pruning.

Git makes rewritten history different.

It does not make rewriting impossible.

The distinction matters because software supply-chain discussions often reach for the strongest available word. Immutable sounds safer than content-addressed. Provenance sounds more reassuring than metadata. Verified sounds more complete than signature valid.

But security comes from knowing exactly what each mechanism says.

A cryptographic signature adds a different kind of evidence.

Git can embed signatures in commits and tags, and it can sign some transactions such as pushes. The signature covers a defined payload. Verification checks whether the signature is mathematically valid for that payload under a key and whether the verifier's trust configuration accepts that key in the relevant way.

That is valuable.

It answers a question ordinary author fields cannot answer: did the holder of this signing credential sign this object?

Even that sentence contains assumptions.

The credential may have been stolen. A signing agent may have been left unlocked. An automated system may hold the key. A corporate SSH certificate may represent an organizational identity rather than one physical person. Trust configuration may be stale. A valid signature can accompany terrible code.

Cryptography can bind an identity claim more strongly to an object.

It cannot certify judgment.

Git's SSH signing support makes the trust problem visible. A verifier can use an allowed-signers file to associate public keys with principals. The file can live outside the repository under each developer's control, or an organization can generate it from an authoritative identity system. Keys can have validity windows. Revocation information can mark keys as no longer acceptable.

The signature format is only half the system.

The other half is deciding whose key counts.

This is why a green Verified badge on a forge should be read carefully. The badge can mean that the platform has validated a signature according to its rules. It does not mean the platform has audited the program's behavior. It does not mean the signer originated every line. It does not mean no automation participated. It does not mean the signer had authority to make the release unless some separate policy grants that authority.

Evidence accumulates in layers.

The commit says what tree and ancestry were recorded.

A signature can say that a credential signed that commit.

A forge can say that the credential is associated with an account under its identity rules.

A protected branch can say that the commit reached a branch through required policy.

A CI system can say that particular checks passed on a particular state.

An attestation can say that a particular builder, workflow, or environment produced an artifact from declared inputs.

A transparency log can make later deletion or equivocation harder to hide.

None of these sentences is equivalent to "the software is safe."

The useful security property comes from composing narrower statements without silently upgrading them.

Software development spent years with a convenient ambiguity because human authorship was usually inferred from context. Alice's laptop made a commit with Alice's configured name. Alice pushed it using Alice's account. Bob reviewed the pull request. The organization knew Alice and Bob. If the repository was small enough, people often recognized the style of the change and remembered the discussion.

The commit itself carried less identity than the social environment supplied around it.

Machine authorship weakens that shortcut.

Suppose Alice asks a coding agent to fix a parser bug. The agent edits five files, generates a test, runs the suite, and creates a commit. What should the author field say?

There is no universal answer because several relationships may matter.

Alice authorized the task.

The agent produced the patch.

A model provider may have supplied the inference system.

A sandbox executed commands.

A CI service tested the result.

Bob may review it.

Alice may ultimately merge it.

Trying to compress all of that into the two traditional identity fields—author and committer—throws information away.

Changing those fields to say "AI" does not solve the problem either. Which agent? Acting for whom? Under what task? Using what permissions? Was the patch regenerated after review? Did a human modify it? Did the final commit preserve the tested tree?

The more useful future is likely additive.

Keep the commit small and stable. Attach richer provenance where the workflow needs it.

That provenance might include a task identifier, the automation identity that produced the change, the human or service that authorized it, the repository state it began from, the checks it ran, and the environment or policy under which it operated. Some information may belong in signed attestations rather than the commit object itself. Some may live in forge metadata. Some may be intentionally omitted for privacy or portability.

The principle is not maximum surveillance.

It is sufficient evidence for the decision being made.

A maintainer reviewing a typo fix does not need a forensic biography of the editor. A security-sensitive release may reasonably demand much more: signed tags, reproducible build information, protected release credentials, builder attestations, and an auditable path from source commit to distributed artifact.

The consequence boundary determines the evidence budget.

This is where commit signing is often oversold and unfairly dismissed at the same time.

It is oversold when a valid signature is treated as proof that code is trustworthy.

It is dismissed when people say signatures are useless because a trusted developer can still sign malicious code.

Both positions ask the mechanism to answer the wrong question.

A signature is useful because it narrows uncertainty about object authorization and identity. If a release tag is expected to be signed by one of a small set of keys, a valid signature can distinguish that release from an unsigned object merely claiming the same name. If a key is compromised, revocation and incident response have something concrete to reason about. If a server account is compromised but the signing key is not, the attacker may be unable to produce the expected signature.

Those are real properties.

They are not code review.

The same discipline applies to commit hashes.

A hash is not a moral property. It is an identity mechanism with cryptographic assumptions. Git's move away from SHA-1 exists because those assumptions age. Chapter 10 described the migration problem: object names have escaped into APIs, databases, documentation, and human practice, so changing the hash function is an ecosystem transition rather than a local implementation swap.

That migration also reminds us that evidence has a lifetime.

A signature algorithm considered strong today may need replacement. A key trusted today may be revoked tomorrow. An account may change hands. A domain may expire. An organization may disappear. A forge may shut down while clones of the repository survive.

Git's portable object graph is valuable partly because it keeps one layer of evidence independent of those institutions.

A commit copied to a new repository is still the same commit under its hash format. Its tree and parents travel with it. An embedded signature travels with the object. External review comments may not. A forge badge may not. An account profile may not.

This suggests a practical hierarchy for durable evidence.

Put the minimum facts needed to identify history in the history itself.

Put cryptographic bindings close enough to the object that they can travel when portability matters.

Put richer workflow evidence in systems designed to express it, but assume those systems may not live forever.

And never let a convenience label erase the difference between integrity, identity, authorization, review, and safety.

These distinctions become especially important in incident response.

Imagine a malicious change appears in a release. Investigators need to ask several separate questions.

Which commit introduced it?

Was that commit part of the branch from which the release was built?

Who or what signed the commit or release tag?

Was the signing credential valid at the time?

How did the commit enter the protected branch?

Which reviews and checks were recorded?

Did the build actually use that source tree?

Was the distributed artifact produced by the expected builder?

Was any credential compromised?

A system that stores only "Verified" cannot answer enough of them.

A system that stores only a detailed CI database but loses the source graph cannot answer enough either.

The commit remains useful because it is a compact anchor around which other evidence can be organized.

That may be one of Git's most important roles in an agent-heavy future.

When software changes arrive faster than humans can remember them, history has to become less dependent on memory. A commit can anchor a claim: this exact tree, with these parents, was proposed or accepted at this point in the graph. Signatures and attestations can attach additional claims to that anchor. Review systems can record decisions around it. Build systems can identify it as an input.

The anchor does not need to know everything.

It needs to remain unambiguous enough for other evidence to point at it.

There is a temptation to solve machine authorship by redesigning the commit object to contain every fact about generation. That would make a twenty-year-old format carry the rapidly changing vocabulary of models, agents, prompts, sandboxes, task systems, and policy engines.

Git's history argues for caution.

Its durable pieces are durable partly because they are narrow.

A tree describes a state.

A commit connects that state to ancestry and metadata.

A ref names a point in the graph.

The social machinery around those primitives has changed repeatedly without requiring every change to become a new object type.

Agent provenance can follow the same pattern if the ecosystem resists the urge to make the commit itself a certificate of understanding.

No commit can prove that.

A human can sign code without reading it. An agent can generate code that passes tests without understanding the business consequence. A reviewer can approve a diff while missing the important line. A build can be reproducible and still faithfully reproduce a vulnerability.

Evidence does not eliminate judgment.

It tells judgment what happened closely enough to make responsibility possible.

That is a more modest promise than trust.

It is also one Git is unusually well positioned to keep.
