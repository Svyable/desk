# The Pull Request

A pull request is not a Git object. That fact is easy to forget because it has become one of the most familiar objects in software development. Developers open one, reviewers comment on it, bots inspect it, continuous integration attaches results to it, security systems scan it, managers count it, and maintainers merge or close it. Then the repository records none of that directly.

Git records commits and ancestry. The pull request is a proposal about those commits, held by the forge. That separation is what allowed it to become much larger than its original job.

The narrow technical problem is simple: one line of history exists somewhere, another is considered canonical, and somebody wants the first incorporated into the second. Git already had several ways to express that desire. A developer could ask a maintainer to fetch a branch. Patches could be sent by email. A signed tag could identify a release or integration point. The Linux kernel community still uses email-centered review heavily because its workflow grew before forge pull requests became universal.

GitHub wrapped the proposal in a durable web object. By August 2010, the company was describing pull requests not merely as requests to merge but as living discussions around code people wanted merged. The proposal was becoming a container for process, and once a repository has such a container, almost every governance problem wants to attach itself there.

Review is the obvious first layer. A reviewer can inspect the difference between the proposed branch and the base branch. Comments can be tied to lines, general discussion can remain attached to the proposal, and later pushes can update the code without erasing the conversation. A patch emailed once is a document sent at a moment in time. A pull request is a moving negotiation.

That persistence is useful because context accumulates, but it creates a version problem. A reviewer's approval can refer psychologically to version three of a branch while version seven is what ultimately merges. Platforms therefore track review state, dismiss stale approvals under configurable rules, and connect checks to specific commit identities. The system has to answer a question Git alone does not ask: approved what?

The same problem appears in continuous integration. A test suite runs against a commit or a synthetic merge result. A check reports success or failure. The forge displays that result on the pull request because the pull request is where the merge decision happens. GitHub's documentation describes status checks as signals that commits meet repository conditions; external systems and GitHub Apps can publish them, and protected branches can require selected checks to pass before merge.

This expansion turned the pull request from a conversation about code into a gate through which code passes. Tests, builds, linting, formatting, type checks, static analysis, dependency review, security scanning, policy validation, documentation generation, deployment previews, and license checks can all report there. The pull request does not perform those judgments. It aggregates them.

Green is seductive precisely because aggregation looks like proof. A screen full of successful checks establishes only that the configured checks reported success under the conditions in which they ran. A missing test remains missing; a race condition may not reproduce; a security problem outside a scanner's model may pass untouched; an architectural mistake can satisfy every automated rule in the repository. Checks reduce uncertainty. They do not eliminate judgment.

Organizations then attached authority to the same object. Branch protection can require approving reviews, status checks, conversation resolution, linear history, signed commits, successful deployments, a merge queue, or other constraints depending on platform configuration. A branch name in Git is just a ref. A protected branch adds an institutional rule about who may move it and under what conditions.

That immediately raises another question: who counts as a competent representative of the code being changed? Some repositories rely on maintainer knowledge. Others assign directories or file patterns to teams or require particular reviewers for security-sensitive paths, deployment configuration, payment code, database schemas, or generated interfaces. On GitHub, a CODEOWNERS file can work with branch-protection rules so designated owners must approve changes touching their paths.

Ownership creates expertise and queues at the same time. A small team responsible for a critical directory may receive every proposal that touches it. If that directory sits low in the dependency graph, unrelated product work can converge on the same reviewers. The rule protecting the code can make those people the throughput limit for the organization.

Pressure then moves back into policy. One approval may be enough for one class of change and absurd for another. Stale approvals may need to disappear after substantive pushes. Administrators may need bypass authority during an incident. Generated files may or may not need the same owners as their source definitions. A mechanical dependency update and a hand-written change to authentication logic can touch the same protected path while carrying very different risks. These are institutional questions expressed through a Git-adjacent interface.

Reality also creates exceptions. A production outage can make the normal review path too slow. A security response may need secrecy that ordinary discussion undermines. A maintainer may be unavailable. A required check may be broken because its service no longer runs. An organization that permits no bypass can discover that its safety mechanism has become an availability risk; one that permits casual bypass has weakened the control into theater.

That is why review systems accumulate audit trails around the rule itself. The useful evidence is not merely that a proposal passed, but whether a requirement was satisfied, dismissed, overridden, or changed while the proposal was in flight. The more governance lives in the pull request, the more the pull request becomes a record of exceptions as well as compliance.

Here the social graph matters in a way the commit graph cannot capture. Two commits can have exactly the same ancestry relationship whether one arrived through months of formal review or through an administrator's direct push. Git preserves the resulting graph. The forge preserves the governance record.

Years later, during a security incident, investigators may ask who approved a change, which checks ran, whether warnings were overridden, whether required conversations were resolved, and whether the branch was protected at the time. None of those answers are guaranteed to exist in the commit object. The commit tells you what tree was recorded, its parents, and claimed author and committer metadata. The pull request tells you how an institution decided to accept it.

That evidence is imperfect. A review can be superficial, an approver can click without reading deeply, a check can be misconfigured, and a branch-protection rule can change. Approval can also decay without anybody doing anything obviously wrong. A reviewer studies a proposal on Monday and approves it; on Tuesday the author pushes a substantial change. Depending on configuration, the platform may dismiss the approval, preserve it, or require another review. If the approval remains visually present, the record can be technically accurate about who clicked and misleading about what that person examined.

Any approval system that allows its underlying object to change after approval has to bind authority to a version. Git gives the forge an unusually strong primitive for doing that because commits have identities. The difficult part is policy: deciding when a change is material enough to invalidate prior judgment and when demanding another pass merely wastes scarce attention. A one-character documentation fix after review and a rewritten authentication path are both new commits. The graph can tell you they differ. It cannot tell you whether the difference deserves another human decision.

The pull request nevertheless captures something Git's core format intentionally does not: the route from proposed change to institutional acceptance. That route grew more elaborate as repositories grew busier, and merge queues are one response.

In a quiet repository, a pull request can be tested against the latest base branch, approved, and merged before the base changes underneath it. In a busy repository, several proposals may be ready at once. Each can be green against yesterday's `main` and still interact badly when merged in sequence. A queue serializes the final act by building a temporary merge candidate, running required checks, and advancing proposals according to policy. Merge order becomes shared state rather than a race for the branch tip.

The queue cannot make independent changes conceptually compatible. If one proposal renames an internal API and another adds a caller using the old name, testing the candidate against the newer target state may catch the break before the protected branch moves. That is valuable, but the queue has learned nothing about why the changes disagree. It has converted an integration surprise into a failed candidate. The organization still has to decide who adapts to whom.

A merge queue is therefore a controlled experiment near the branch tip, not an automatic integrator. It can make order explicit and prevent a green proposal from turning red only after landing. It cannot decide architecture, preserve intent, or reconcile contradictory product choices.

Git made divergent histories inexpensive to create. Integration remains expensive because convergence is partly semantic. A merge algorithm can determine whether lines overlap mechanically. It cannot decide whether two independently reasonable changes contradict product strategy, whether compiling code violates an undocumented operational assumption, or whether a new abstraction belongs in the codebase. Human review became the social answer, and scale made human review itself a bottleneck.

Large organizations accumulated review rotations, ownership rules, specialist approvers, automated reviewers, labels, bots, stale-change rules, size limits, queues, and service-level expectations. A developer can spend less time writing a change than navigating the process that decides whether it enters `main`. That is not necessarily bureaucracy gone wrong. A repository used by three people can rely on conversation; one used to ship a bank, operating system, cloud service, medical device, or widely consumed library may need explicit evidence that somebody responsible considered the change.

The word evidence matters more than proof. A pull request can show that a process happened. It cannot show that the process was wise. A test suite can encode the wrong assumptions, a reviewer can share the author's blind spot, a code owner can be overloaded, a scanner can lag a new exploit class, and a merge queue can faithfully serialize a bad decision. Governance systems reduce classes of error. They do not abolish error.

They can also turn familiar procedure into legitimacy. A proposal that crosses the required path looks governed because the path is recognizable. Teams then risk optimizing for the ritual: the reviewer writes “LGTM” because an approval is required; an author splits a risky change into pieces because smaller proposals move faster even though the risk exists only in the combined behavior; a bot comments on every dependency update until humans stop reading; a flaky required test gets rerun until green instead of repaired. The pull request did not create these behaviors. It made them observable.

Observable process is easy to count. Organizations can measure time to first review, time to merge, approvals, comments, check duration, queue depth, and pull-request volume. Those measures can reveal real bottlenecks, but a ten-minute review is neither good nor bad in the abstract, twenty comments may be a healthy design discussion or a poorly prepared change, and hundreds of daily pull requests may indicate exceptional throughput or a workflow manufacturing tiny administrative units because the metric rewards them. The forge sees events more easily than it sees understanding.

That gap becomes more important as authorship gets cheaper. Monorepos already produced review pressure through organizational scale. Large open-source projects produced it through contributor volume. Automated dependency systems, formatting bots, and generated code added proposal traffic with little human intention behind each line. Coding agents intensify the same problem.

If a machine can produce a plausible patch in minutes, branch creation becomes nearly free in both the technical and labor senses. The expensive object is the reviewer's attention. A machine author can try several implementations, run tests on all of them, and present whichever survives. It can continuously create follow-up fixes, dependency bumps, refactors, documentation updates, and cleanup changes. The repository can store this volume. The institution may not be able to judge it.

That creates an obvious temptation: automate more of the decision. Agents can write code, other agents can review it, checks can arbitrate disagreement, and a merge queue can integrate what survives. For some classes of change that pipeline may be appropriate. It can also create a closed epistemic loop in which machines generate, evaluate, and accept work using tests and models derived from the same incomplete specification. A green pull request may become less informative as production becomes cheaper; the number of checks can rise while the amount of human understanding falls.

This does not mean every change needs manual line-by-line inspection. It means a proposal needs to carry more than a diff when authorship becomes abundant: why the change exists, which constraint it is meant to satisfy, what alternatives were attempted, which behaviors should change, what evidence supports that expectation, and what would justify reverting it. A human author often carries these answers implicitly and supplies them during review. An agent can generate them too, but the system still has to decide which claims are trustworthy and how they relate to the actual commits.

The next generation of pull-request tooling can grow around Git rather than inside it. Semantic summaries, generated test rationale, provenance, execution traces, dependency impact, ownership inference, behavior-level diffs, and agent task context can all attach to the proposal. The danger is familiar: every new signal is useful because it compresses complexity, and then organizations begin depending on the compressed signal and forgetting what it omitted.

Green checks did not eliminate bugs. Approvals did not eliminate shallow review. Branch protection did not eliminate bad merges. Machine summaries will not eliminate misunderstanding. The durable value of the pull request is simpler: it gives proposed change, evidence, and authority one place to meet before a branch becomes shared history.

The next problem is what happens when the repository itself becomes too large for the assumptions under that institution. The graph may have no center. At monorepo scale, it can still become very heavy.
